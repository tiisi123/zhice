# 事故与回滚预案

## 事故分级

| 等级 | 说明 | 处理要求 |
| --- | --- | --- |
| S1 | 登录、支付、核心行情全不可用 | 立即回滚或热修 |
| S2 | 短线核心部分不可用 | 30 分钟内定位，必要时回滚 |
| S3 | 单页面展示异常 | 当日修复 |
| S4 | 文案、样式、非核心问题 | 排期修复 |

## 常见事故

| 场景 | 快速判断 | 处理 |
| --- | --- | --- |
| 涨停/炸板为空 | 跑 `check_realtime_sources.py` | 确认数据源、服务是否重启 |
| 页面显示 mock | 跑 `check_no_mock.py` | 立即移除 mock 或标记为示例 |
| API 字段缺失 | 跑 `check_api_contract.py` | 修 route 响应或重启服务 |
| WebSocket 无更新 | 检查 `/api/ws` 和 `ws_hub` 日志 | 重启 API，确认代理 upgrade |
| 数据库锁定 | 检查 SQLite WAL 和 worker 数 | 保持单 worker，必要时切 PostgreSQL |

## 回滚步骤

1. 确认影响范围和事故等级。
2. 停止继续合并相关分支。
3. 找到上一个稳定 tag 或 commit。
4. 判断是否涉及数据库 schema。
5. 回滚后端和前端产物。
6. 重启 API 和调度器。
7. 跑 smoke test 和实时数据检查。
8. 记录事故原因和后续 action。
